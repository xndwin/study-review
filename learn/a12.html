第 12 周：提取服务、缓存、用量

请求怎么走缓存键比较两个提示失败时沿着链路看这一周自己写

计划日期：2027-02-01 到 2027-02-07。

把提取接到工单服务上。同一批样本能再跑一遍。报告里有正确数、总数、错误类别、耗时和用量。缓存要把模型、供应商和提示版本分开。

请求怎么走

一条反馈进来：写入参 → 拼提示 → 调模型 → 校验字段 → 合格才写入数据库，不合格记为转人工或错误。

单元测试用假的模型响应，不花钱。真实 API 另开一个命令，跑完把费用记下来。

每个请求生成一个 request_id，写进日志。失败时你能用这个编号把输入、供应商、提示版本和错误对上，而不是在一堆输出里猜。

缓存键

相同输入不必重复付费。键至少包括：

  • 供应商
  • 模型名
  • 提示文件的版本或内容摘要
  • 用户输入

只按用户输入缓存，换了提示还会返回旧提取。缓存内容是已经通过字段校验的结果，或者明确的失败原因。不要把密钥放进键。

比较两个提示

提示 A 和提示 B 用开发集跑。表格列：版本、格式正确、内容正确、平均耗时、prompt_tokens 合计、completion_tokens 合计。保留集只在你选定一个版本之后跑一次。

限流沿用第 9 周的重试上限。另外给这一次批量设一个总 token 预算，超过就停，避免循环把额度打完。

失败时沿着链路看

拿一条失败输入，按顺序问：

  1. 数据库里的原始输入是不是这句话？
  2. 发出去的提示是哪一版？
  3. 模型原始响应是什么？
  4. 是 JSON 坏了、字段不合格，还是类别和标注不一致？
  5. 有没有写进错误表，而不是悄悄丢了？

改提示只能处理「模型看懂了但选错类别」这一类。字段缺失、超时、写错数据库，改提示没用。

这一周自己写

工单上增加「从描述提取类别」。同一条描述调用两次，第二次命中缓存，不再增加用量。换提示版本后，同一条描述会重新调用。

验收：一份报告包含两家供应商或两个提示版本；数字是计数，不是「效果很好」。你能拿一条失败样本走完上面五步。
