第 21 周：换环境仍能启动

计划日期：2027-04-05 到 2027-04-11。

两个项目都在干净环境里重新部署。启动、停止、出了问题看哪里，写成说明。不依赖你电脑上的绝对路径。服务重启不丢状态。

目标岗位的招聘说明里写了 MCP，才额外加一个只读工具。没做 MCP，不挡住这一周。

配置

密钥、数据库地址、模型名、端口都来自环境变量。仓库里是 .env.example，值是占位符。

依赖写进 requirements.txt，版本用你测试通过的那一版，不要写没有上限的「最新」。别人安装的是你锁定的版本。

索引文件和数据库文件的路径相对项目根目录，或者由环境变量给出。代码里不要出现 /Users/... 这种只有你机器上才有的路径。

向量索引旁边仍然记着 embedding 模型名。换机器之后，模型名对不上就重建，不把旧文件拷过去硬搜。

启动说明写这几段

  • 需要的软件：Python 版本、Docker。
  • 复制哪一个示例配置，要填哪几个变量。
  • 一条启动命令，一条停止命令。
  • 怎样知道服务已经好了：打开 /health 得到 200。
  • 数据在哪个卷或哪个文件。docker compose down 之后再 up，工单和待确认任务还在。
  • 三个常见失败：端口占用、缺少环境变量、数据库还没接受连接。每一种贴一条你真实见过的日志，并写你改了什么。

MCP 只在岗位点名时做

MCP 是让外部客户端按一份协议调用你的工具。如果要做，只暴露一个只读工具，例如按编号查已经允许该用户看的政策。不暴露执行 SQL、不暴露写工单。做完在笔记里写岗位链接和日期。岗位没提，就跳过。

这一周自己写

找一台不是你日常目录的位置，或者把项目拷到一个新文件夹，只按 README 启动两个项目。把卡住的步骤补进 README，再从头走一次。

验收：新位置不改源码就能跑；重启后待确认的草稿还在。
