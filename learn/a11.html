第 11 周：向量、评测集、三种改知识的办法

计划日期：2027-01-25 到 2027-01-31。

这一周把「调用 API」「检索」「微调」分开，并建立大约 50 条你亲自看过的提取样本。格式正确和内容正确要分开数。

三种改知识的办法

办法改变什么什么时候用
把资料放进 prompt 或先检索这一次请求看得到的文字制度、手册会更新
微调模型权重要稳定的格式或语气，且有成对数据
只调 API不增加新知识翻译、归纳用户刚刚给的文字

提取用户刚刚贴来的反馈，属于第三次。模型不需要记住你的产品手册。知识库问答才需要检索。微调不是这半年的主线。

向量在比什么

一段文字可以变成一串数字，叫 embedding。两段话越接近，两个向量的夹角越小。余弦相似度看的是方向，不是向量有多长。

cosine([1, 0], [1, 0]) 是 1。cosine([1, 0], [0, 1]) 是 0。真实 embedding 的长度由模型决定，不同模型的向量不能放在同一次比较里。

词匹配是另一条路：问题里的词和段落里的词重叠多少。它不需要 API，能先当基线。向量换的是「怎样把文字变成可以比较的东西」，后面的「取前几名、拼进提示、生成」可以不变。

tokenization 是把文字切成模型内部的片段。Attention 是模型在生成下一个片段时，给前文分配权重。这两个词能解释即可：token 不是字；模型不是在数据库里查找你的 PDF。

评测集怎么分

自己写大约 50 条反馈，每条标明类别、产品、问题描述。你要真的读过，不能让模型先生成再拿来当标准答案。

分成两份：

  • 开发集大约 30 条。改提示、改规则时只看这一份。
  • 保留测试集约 20 条。定稿前只跑一次，不拿它调提示。

一条样本记两列：

  • 格式：是不是合法 JSON，字段在不在，类别在不在允许列表。
  • 内容：类别和产品是否与你标的一致。

格式对了、类别判错，算内容错，不要合成一个含糊的总分。报告写「内容 16/20」，分母一起写。

数据泄漏是指测试题已经出现在提示的例子里，或你反复用测试集改提示。那样的分数不能当成第一次见面的成绩。

这一周自己写

  • 一个不调用模型的 cosine，用上面的两个向量核对 1 和 0。
  • 50 条样本落到 eval/dev.jsonl 和 eval/holdout.jsonl。
  • 脚本对一份假的模型输出计算格式正确数和内容正确数。

验收：你能口头说明 API 调用、检索、微调各解决什么；能指出某条是格式错还是内容错。
